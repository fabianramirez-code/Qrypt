# Threat Model

What can expose or break Qrypt's security, and how the design answers each threat.

The cryptographic algorithms are the least likely thing to fail. Realistic attacks go around them: against the user's device, the passphrase, the vault directory and its mirror, and Qrypt's own code.

> **Status:** the defenses are marked below. Implemented: Argon2id and the recovery phrase (2), locked and wiped memory and the self-clearing clipboard (1, 7), the signed manifest and rollback record (3), opaque names and encrypted metadata (7), and signed releases (6). Planned: the signed member list and trust root (3), key rotation for removed members (4), and the independent review (5). Not audited.

## Starting assumptions

- **The vault directory and its mirror are not trusted.** Qrypt assumes an attacker can read them and may be able to write to them, for example through a synchronized folder.
- **One identity opens everything.** Personal and work secrets live in one place, so a stolen identity exposes both at once. This is why the first two threats weigh the most.

## Threats at a glance

Ordered from most to least likely.

| #   | Threat                                     | Main defense                                                    |
| --- | ------------------------------------------ | --------------------------------------------------------------- |
| 1   | Infected device                            | Limit what is exposed while unlocked                            |
| 2   | Weak passphrase or exposed recovery phrase | Argon2id, generated passphrase, recovery phrase on paper only   |
| 3   | Tampering with the vault or its mirror     | Signed manifest per scope (member list planned)                 |
| 4   | Copies keep old access                     | Rotate scope keys and the real secrets (planned)                |
| 5   | Mistakes in Qrypt's own cryptographic code | Published constructions, official test vectors, external review |
| 6   | Supply chain                               | Few pinned dependencies, signed releases                        |
| 7   | Leaks around the encrypted content         | Opaque names, encrypted metadata, clipboard exclusion           |

## 1. Infected device

**Attack:** malware on the user's machine records the passphrase as it is typed, or reads memory or the clipboard.

**Defense:** no password manager withstands this. Qrypt can only reduce the damage:

- Lock automatically.
- Decrypt only the secret the user asks for, never the whole vault.
- Wipe secrets from memory after use and clear the clipboard.

**Limit:** Long-lived identity and scope key bytes live in best-effort locked, wiped pages. This reduces exposure to swap and hibernation files and, on Linux, core dumps. Lock or allocation refusal does not block use; the unlocked vault warns when protection is refused. Typed secrets and clipboard-held values still live in TUI strings; Bubble Tea delivers key events as strings, and revealed values require a string while drawn. Go runtime and cryptographic-library copies are not protected. It does not defend against a live attacker with the same privileges or a debugger.

## 2. Weak passphrase or exposed recovery phrase

**Attack:** the identity file is the only thing protected by a secret that a person chooses. Anyone who copies it (a stolen machine, a cloud backup, a configuration folder copied by accident) can guess passphrases offline without limit.

The recovery phrase is worse: it is the complete key and bypasses the passphrase, so a photo of it is enough.

**Defense:**

- Argon2id with high parameters, to make each guess expensive.
- A passphrase generated by Qrypt: 7 random words. People choose weak passphrases, so Qrypt does not let them choose. See [Passphrase](identity.md#passphrase).
- The recovery phrase is shown once and kept on paper only.

## 3. Tampering with the vault or its mirror

**Attack:** anyone with write access, including someone who controls the synchronized folder or its account, can change files. Two attacks matter most:

- **Key substitution:** add the attacker's public key to the member list, so the next encryption also includes the attacker.
- **Rollback:** restore an old version, for example one that still lists a removed member.

**Defense:**

- Planned, with sharing: a signed member list, verified against a trust root stored on the user's machine.
- Implemented: a signed [manifest](vault.md#6-integrity) of the current state of each scope, and a record on the user's device of the last generation seen, so a client can detect a removed file or a rollback. Qrypt keeps no log of past states.

## 4. Copies keep old access

**Attack:** whoever had access keeps the encrypted copies and the keys from that time (older mirror versions, backups). Removing a member does not remove what they already saw.

**Defense (planned, with sharing):** rotate the scope key and tell the user that the real secrets of that scope have to be changed. Qrypt does not list them. See [Removing a member](key-model.md#removing-a-member).

## 5. Mistakes in Qrypt's own cryptographic code

**Attack:** this is far more likely than breaking ML-KEM. Examples:

- Reusing a nonce (a number that must be unique for every encryption).
- Combining the two hybrid keys incorrectly.
- Not binding a secret to its location, which would let an attacker swap one secret for another.

**Defense:**

- Invent nothing: use published, publicly reviewed constructions, such as X-Wing for the hybrid key encapsulation.
- Check the implementation against official test vectors.
- Get an external review before anyone stores real data.

## 6. Supply chain

**Attack:** a compromised dependency or a modified release binary delivers the malware from threat 1 to every user. Maintainer accounts on GitHub become targets.

**Defense:**

- Few dependencies, with pinned versions.
- Signed releases.
- Two-factor authentication on maintainer accounts.

## 7. Leaks around the encrypted content

**Attack:** encryption hides the content, not everything around it.

- The synchronized folder or backup still shows file sizes, dates and how many files exist. Names are opaque and encrypted, but the count and size of the files are visible.
- Clearing the clipboard does not reach copies kept by clipboard history or cloud clipboard sync.

**Defense:**

- Opaque file names and encrypted metadata.
- Mark copied secrets as excluded from clipboard history where the operating system allows it.
